## 3. 审查发现与处理

| 编号 | 级别 | 发现 | spec 依据 | 处理 |
|---|---|---|---|---|
| F3-1 | 缺陷 | `saveSnapshot` **编辑路径**不做同分钟冲突检查：把快照编辑到另一条快照所在分钟可直接保存（UI 层有拦截，但数据层是最终防线，绕过 UI 的调用可写入违反不变量的数据） | 02 §3.4.3"同一分钟只允许一条" | **已修复**：冲突检查前置到新增/编辑共同路径、排除自身（红→绿） |
| F3-2 | 待澄清 | 编辑旧快照时：① 表单只遍历活跃账户，已软删除账户的 entry 会从该快照中**静默消失**；② totalCents 按**当前**账户设置重算——与 02 §5.4.3"不按当前账户设置重算历史"的口径存在张力。spec §3.4.5 仅说"总资产重新计算"，未明确以何时点的账户设置为准 | 02 §2.4.7、§3.4.5、§5.4.3 | 记录，建议 spec 明确编辑口径（推荐：编辑保留原 entries 中非活跃账户的值，只更新活跃账户），本次不改行为 |
| F3-3 | 缺陷（UI） | SnapshotHistoryModal.accountName 对已删除账户显示「未知账户」：store.load 过滤了软删除账户，`account.deletedAt ? 名称（已删除） : 名称` 分支永远走不到（死代码） | 02 §2.4.7"显示为原账户名并附「已删除」标记" | 记录待修：建议 store 保留全量账户或组件按需查询 accountsRepo；UI 层缺陷由浏览器验收/E2E 阶段复验 |
| F3-4 | 待澄清 | ±50% 大幅变化确认仅在**新增**快照时触发（`!editSnapshot` 条件），编辑快照跳过确认；02 §3.4.3 防呆规则未区分新增/编辑场景 | 02 §3.4.3 | 记录，建议 spec 明确 |
| F3-5 | 轻微 | 生产构建单 chunk 1.8MB（ECharts/antd 未分包），build 有 >500kB 警告 | 工程质量 | 记录，后续用 manualChunks 分包 |
