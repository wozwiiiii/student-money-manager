## 1. 背景与问题

### 1.1 观察到的问题

中国大学生的资金与理财信息分散在至少三类平台：微信生态（零钱 / 零钱通、理财通）、支付宝生态（余额宝、平台上购买的基金与理财）、银行（银行卡活期存款、定期存款与银行理财）。由此产生四个可观察的问题：

| 编号 | 问题 | 具体表现 |
|---|---|---|
| P1 | 资产总貌不可见 | 想知道"我一共有多少钱"，需要打开三个以上 App 分别查看余额后手动相加；没有任何一个平台给出全量视图 |
| P2 | 账单互不覆盖 | 每个平台各自记账，但都不完整：现金消费不进任何平台账单；银行卡消费不进支付宝账单；想看"这个月总共花了多少"没有单一入口 |
| P3 | 缺少匹配生活费节奏的预算工具 | 主流记账产品按自然月设计预算，而大学生的资金以"学期初/月初一次性到账、多周匀速消耗"为节奏，且存在学期这样的天然规划周期 |
| P4 | 小白缺少可信的教育入口 | 各理财平台的内容默认用户已理解货币基金、定期理财、风险等级等概念；面向零基础学生的体系化科普内容稀缺 |

概念说明（本套文档各处沿用）：零钱通、余额宝在产品形态上是零钱理财工具，底层为**货币基金**（一种主要投资于短期存款、债券等低风险品种的基金，收益较低但波动小、可快速取出使用）；**定期理财**指资金需存放满约定期限后才能取出的产品（通常收益高于活期，展示的收益率为参考值而非承诺，提前取出受限制）。

### 1.2 受影响用户与时刻

| 时刻 | 用户面临的具体处境 | 对应问题 |
|---|---|---|
| 生活费到账日（月初或学期初） | 一笔钱到账，需要规划未来数周怎么分配，但没有工具承载"这笔钱怎么花、存多少" | P3 |
| 每次消费后 | 记不清钱花在了哪；部分消费（现金、跨平台）无处记录 | P2 |
| 月末 / 学期末复盘 | 想知道钱花去了哪里，账单分散在多个 App，逐个翻看后仍拼不出完整的分类统计 | P2、P3 |
| 学期中查看储蓄进度 | 为某个目标（换电脑、旅行、毕业基金）攒钱，攒的钱散在多个平台，进度靠心算 | P1 |
| 首次尝试理财（活期转定期 / 买入基金） | 看不懂产品说明中的术语，不敢操作，或在不理解的情况下盲目操作 | P4 |

### 1.3 产品决策（与问题一一对应）

| 问题 | 产品决策 | 详见 |
|---|---|---|
| P1 资产总貌不可见 | 提供资产总览页：用户登记账户并更新资产快照，页面展示总资产、账户结构与资产趋势图 | 第 5.1、5.2 节，第 6 章 |
| P2 账单互不覆盖 | 收支记录支持手动录入 + 支付宝/微信账单 CSV 导入 + 银行流水文件导入，合并为统一收支记录，生成收支分类占比图 | 第 5.3、5.4 节 |
| P3 预算工具不匹配 | 预算周期支持月度与自定义周期（如学期）双维度，两套视图并存、可切换查看 | 第 5.5 节 |
| P4 缺少教育入口 | 全部投资相关内容定位为教育性信息、不构成投资建议；投资概念首次出现附浅白解释；配置示例只做比例示意、不涉及具体产品推荐 | 第 4 章约束 4、5 |

### 1.4 可观察的预期结果

以下均为可在产品界面上直接观察到的行为，不使用"提升体验"等不可验证的表述：

1. 用户登记至少 2 个账户并完成 2 次资产快照更新后，资产总览页展示这段时间的资产趋势图。
2. 用户导入某月支付宝或微信账单 CSV 后，该月收支分类占比图包含导入的数据；分类由映射规则自动匹配，无需逐笔手动选择（未能匹配的笔数在页面上单独提示）。
3. 用户在同一页面可在"月度"与"自定义周期（如本学期）"两个视图之间切换，两套预算进度同时可见。
4. 用户创建储蓄目标并更新已储蓄金额后，目标卡片展示进度百分比与剩余天数。
5. 每个投资类概念（货币基金、定期理财、净值、风险等级等）在页面中首次出现的位置，均伴随一句浅白解释。
6. 当某分类支出接近或超出该周期预算时，页面顶部出现提示条，且对应预算卡片内的进度条高亮显示。
7. 用户首次使用时，页面明确告知：数据存储于浏览器本地、支持导出备份文件、不支持多端云同步。

## 2. 目标用户画像

### 2.1 主画像：理财小白（设计中心）

| 维度 | 描述 |
|---|---|
| 本金规模 | 以几千元以内为主，来源于每月生活费的结余；具体人群规模与分布 [TBD]，不做未经调研的数字引用 |
| 资金存放特征 | 余额宝 / 零钱通（两者底层均为货币基金）与银行卡活期为主；部分持有银行定期存款、银行理财或理财通理财；少部分持有场外基金（指通过支付宝、微信、银行等渠道申购和赎回、而非在证券交易所内买卖的基金） |
| 认知起点 | 未系统学习过理财知识；对货币基金、定期理财、净值、风险等级等概念不清楚或仅模糊听说（风险等级即行业常见的 R1～R5 分级，R1 风险最低、R5 最高 [映射细则 TBD]）；使用理财 App 的行为以查余额为主，基本不用行情与分析功能 |
| 理财目标特征 | 目标以中短期（一个学期至一两年）、有具体用途（换数码设备、旅行、应急备用金、毕业过渡金）为主；态度上本金安全优先于收益追求 |
| 使用行为特征 | 低频查看资产（以周为单位，而非盯盘式实时查看）；对操作步骤的复杂度敏感，遇到不理解的概念倾向于放弃而不是自行查证 |

### 2.2 次要用户（可使用、但非设计中心）

| 用户群 | 与主画像的差异 | 产品上的覆盖方式 |
|---|---|---|
| 已持有场外基金、想要统一记账的学生 | 认知起点高于主画像 | 基金持仓类账户与资产快照覆盖其记录需求；教育内容对其偏基础 |
| 临近毕业、需要规划过渡资金的学生 | 目标的时间维度更长（毕业后 3～6 个月） | 自定义预算周期与储蓄目标可承载；不为其单独设计功能 |

[Assumption, TBD] 主画像与次要用户在目标人群中的占比未做调研，无法给出比例。

### 2.3 明确不服务的用户

| 用户群 | 不服务的原因 |
|---|---|
| 需要多端实时同步的用户 | 产品无账号、数据存浏览器本地、不支持云同步（见第 4 章约束 3） |
| 需要实盘股票交易或个股投资建议的用户 | 股票模块为信息层，无交易、无建议（见第 4 章约束 2、4） |
| 持有黄金等贵金属及另类资产的用户 | 资产类型范围明确排除此类资产（见第 6.1 节） |

## 3. 核心使用场景

### 场景 1：月初领生活费做预算

| 要素 | 内容 |
|---|---|
| 触发时机 | 每月生活费到账当天（通常为月初） |
| 用户动作 | 打开应用 → 进入本月预算周期 → 设置总预算金额 → 设置各分类（餐饮、购物、学习等）的预算金额 |
| 产品响应 | 展示预算编辑页，预置常用分类模板；支持从上月预算一键复制后修改；保存后预算总览卡片显示总预算与各分类预算，进度均为 0% |
| 完成标志 | 当月预算视图中可见总预算与各分类预算金额；后续每笔支出记录计入对应分类的预算进度 |

### 场景 2：日常记一笔

| 要素 | 内容 |
|---|---|
| 触发时机 | 一笔消费完成后（当场记录，或当晚集中补记） |
| 用户动作 | 点击记一笔 → 选择分类（近期用过的分类置顶显示）→ 输入金额 → 可选填写备注与所属账户 → 保存 |
| 产品响应 | 表单日期自动填充为当天；保存后页面显示保存成功提示；对应分类的预算进度条立即更新 |
| 完成标志 | 该笔记录出现在收支记录列表中；若该分类支出因此接近或超出预算，页面顶部与预算卡片内出现高亮提示 |

### 场景 3：月末导入支付宝/微信账单 CSV 对账复盘

| 要素 | 内容 |
|---|---|
| 触发时机 | 月末或次月初 |
| 用户动作 | 在支付宝/微信中导出上月账单 CSV 文件（平台自带功能，产品内提供操作指引）→ 在本应用中导入该文件 → 检查分类映射结果 → 确认导入 |
| 产品响应 | 读取文件内容并展示预览列表；按映射规则自动匹配分类（如账单描述含"食堂"归入餐饮），未匹配项可批量指定分类；与已有记录疑似重复的条目（同日期、同金额、同描述 [判定规则细节 TBD]）被标记出来，供用户选择跳过；导入完成后展示该月收入/支出总额与收支分类占比图 |
| 完成标志 | 当月收支分类占比图包含导入数据；用户可看到该月支出金额排名前三的分类及各自金额 |

### 场景 4：学期储蓄目标进度查看

| 要素 | 内容 |
|---|---|
| 触发时机 | 学期中任意时刻（用户不定期查看） |
| 用户动作 | 打开储蓄目标页 → 查看（或手动更新）目标进度 |
| 产品响应 | 目标卡片展示：目标名称、目标金额、已储蓄金额、进度百分比、剩余天数；已储蓄金额支持手动更新，或关联所选账户的资产快照自动取值 [关联取值方案 TBD] |
| 完成标志 | 用户看到当前进度百分比，以及按当前节奏的完成预期提示（如"按每周存入 ¥X 的节奏可按期达成"） |

### 场景 5：查看资产总览

| 要素 | 内容 |
|---|---|
| 触发时机 | 不定期，典型为每周一次，或理财产品到期、余额发生变动时 |
| 用户动作 | 打开资产总览页 →（可选）点击"更新快照"，逐账户填入当前余额 → 保存 |
| 产品响应 | 展示当前总资产金额、按账户的账户结构（现金与活期 / 定期与理财产品 / 基金持仓）、最近一次快照的时间标记；存在 2 次以上快照时展示资产趋势图；页面不出现任何"实时余额"字样 |
| 完成标志 | 用户能够回答"我现在一共有多少钱、分别放在哪里"；页面显示最近快照更新时间 |

### 场景 6：首次进入的初始化设置

| 要素 | 内容 |
|---|---|
| 触发时机 | 首次打开应用 |
| 用户动作 | 按引导依次：创建账户（如"余额宝""银行卡"）并填入当前余额 → 可选设置本月预算 → 可选完成风险偏好自评 |
| 产品响应 | 分步引导表单，每一步均可跳过；首次展示本地存储说明、备份文件导出入口与"教育性信息，不构成投资建议"声明；完成后生成第一条资产快照 |
| 完成标志 | 资产总览页显示所填账户与总资产；若全部跳过，页面显示引导用户开始的占位提示 |

## 4. 第一性原理硬约束分析

本章记录 5 条不可绕过的外部约束，并逐条按"硬约束 → 推导出的产品决策 → 该决策的代价/取舍"推导。这 5 条约束是本产品全部形态决策的出发点。

### 约束 1：主流理财平台不向个人第三方应用开放资产查询接口

**硬约束**：微信理财通、支付宝、各大银行均不向个人第三方应用开放资产查询接口。

**推导出的产品决策**：
- 数据获取只提供两条通道：手动录入与文件导入（支付宝/微信账单 CSV、银行流水文件），不承诺任何形式的自动同步。
- 产品围绕"低频快照更新"而非"实时同步"设计：资产总览由用户主动更新的资产快照驱动，页面标注最近更新时间，不出现"实时"字样。
- 不提供任何依赖自动同步的功能（如余额变动自动提醒、自动对账）。

**代价 / 取舍**：
- 数据新鲜度取决于用户的更新频率；用户长期不更新时，总览展示的是历史快照（因此"最近更新时间"必须始终可见）。
- CSV 导入要求用户先学会在支付宝/微信中导出账单，存在一次性学习成本（以产品内操作指引对冲）。
- 用户若期望"自动记账"，该期望在本产品中无法满足；需在产品说明中明确告知，避免形成错误预期。
- 长期使用依赖用户手动维护数据的意愿，维护成本由用户承担。

### 约束 2：无法对接券商实盘交易

**硬约束**：无法对接券商实盘交易。

**推导出的产品决策**：
- 股票模块（P1 二期）定位为信息层：自选股列表 + 行情展示 + 基础分析，仅此而已。
- 不提供买卖入口、不接入真实持仓、不输出"买入/卖出/持有某股票"的建议。
- 行情数据来源与延迟性明确标记 [TBD]；分析结果一律附带"教育性信息，不构成投资建议"声明。

**代价 / 取舍**：
- 用户无法在本产品内看到自己的股票实盘持仓，股票分析只能围绕自选股展开。
- 分析深度受限于公开行情数据；涉及个股的结论性判断（估值高低、买卖点位）不在范围内。
- 股票模块是纯内容消费型功能，不与用户的实际资金操作形成闭环。

### 约束 3：个人小应用资源有限

**硬约束**：产品由个人/极小团队维护，可用于后端运维与长期维护的资源有限。

**推导出的产品决策**：
- 无账号、本地优先：数据存储在用户浏览器本地；提供备份文件导出，由用户自行保管。
- 不支持多端云同步；不提供任何需要后端持续运行的功能。

**代价 / 取舍**：
- 用户清除浏览器数据或更换设备会导致数据丢失，"导出备份文件"是唯一补救手段，且备份责任在用户（产品须在首次使用时明确告知）。
- 浏览器本地存储容量有限，产品设计不承诺无限期保留全部导入的账单明细（容量对应的数据保留策略 [TBD]）。
- 多设备使用的用户无法获得一致数据，属于明确放弃的服务范围（见 2.3）。

### 约束 4：内容涉及投资

**硬约束**：产品内容涉及投资，表述必须避免构成投资建议；银行产品信息只能基于公开信息整理。

**推导出的产品决策**：
- 全部投资相关内容（配置教育、股票分析、银行产品信息）统一标注"教育性信息，不构成投资建议"，并在首次进入相关模块时显著展示。
- 配置教育中的示例只做比例示意（如按风险等级给出"活期 / 定期 / 基金"三类资产的示例比例区间），不点名任何具体产品。
- 银行产品信息库为公开信息的人工整理：每条信息标注来源与整理日期；未能核实的数值（如具体利率、费率）一律标记 [TBD]。

**代价 / 取舍**：
- 无法回答"我该买哪个产品"这类高频问题，部分用户预期不被满足。
- 公开信息需人工收集与更新，信息库的规模与时效受人力限制，P1 阶段先以精选少量产品起步 [数量 TBD]。
- 示例比例必须配合充分的限定语表述，内容制作成本高于直接给结论的写法。

### 约束 5：目标用户是理财小白

**硬约束**：目标用户是理财小白，不具备投资概念基础。

**推导出的产品决策**：
- 投资类概念（货币基金、定期理财、净值、风险等级等）在界面中首次出现的位置，以括号或说明区给出一句浅白解释；本套文档同样遵守此规则。
- 风险等级同时展示浅白描述与等级标签（低 / 中低 / 中 / 中高 / 高），并解释与常见评级 R1～R5 的对应关系 [映射细则 TBD]。
- 配置示例只做科普性比例示意，不涉及具体产品推荐（与约束 4 叠加生效）。
- 分类、预算等处提供适合学生生活的默认模板，降低从零配置的成本。

**代价 / 取舍**：
- 解释文本增加界面信息密度，需以"默认一句、点击展开详情"的方式控制 [展开样式 TBD]。
- 浅白解释是压缩表达，牺牲部分精确性；关键概念另行链接权威释义来源 [来源 TBD]。
- 为小白设计的默认值对有经验用户略显冗余，由自定义设置覆盖。

## 5. 共享概念唯一定义

本章为全套文档的术语基准。以下 7 个概念在套件内只以本章定义为准，其他文档引用时不再重定义。

### 5.1 账户

**定义**：用户在本应用中创建的、对应现实中一个资金存放渠道的记账容器（如"支付宝余额宝""微信零钱通""某银行卡""某银行定期"）。

**关键属性**：

| 属性 | 说明 |
|---|---|
| 账户名称 | 用户自定义，创建时提供常用默认名 |
| 资产类型 | 三选一：现金与活期（含余额宝/零钱通等货币基金类零钱理财）、定期与理财产品（含理财通理财、银行定期存款与银行理财）、基金持仓（场外基金） |
| 是否计入总资产 | 默认计入；可单独设置为不计入（如长期闲置账户） |
| 当前余额 | 不作为账户的固有属性存储，始终取自该账户最近一次资产快照 |

**与相近概念的区别**：账户是持续存在的"容器"，资产快照是对容器内余额的"时点测量"；账户回答"钱放在哪里"，分类回答"钱花在了什么上面"，两者是不同维度。

### 5.2 资产快照

**定义**：用户在某一时刻手动录入的、覆盖其所登记账户的余额时点记录。一次快照 = 一个时间点 + 各账户余额 + 总资产。

**关键属性**：

| 属性 | 说明 |
|---|---|
| 快照时间 | 用户执行更新操作的时刻 |
| 各账户余额 | 该时刻每个账户的余额；其中基金持仓按净值（每份基金单位的价格，持有金额随净值涨跌变化）折算为当时价值；定期与理财按产品展示的当前价值折算 [估值口径 TBD] |
| 总资产 | 计入统计的账户余额之和 |
| 数据来源 | 手动录入 |

**与相近概念的区别**：资产快照是**时点存量**（"某刻一共有多少"），收支记录是**区间流量**（"一段时间内进出多少"）。两者不能互相推算：基金净值波动会改变快照金额，但不构成一笔收支；从银行卡转钱到余额宝会在两个平台各自的账单中留下记录，却不改变总资产。因此资产趋势图与收支统计图是两套独立计算的结果，可并列对照、互不推导。

### 5.3 收支记录

**定义**：一笔资金进出事件的记录，由手动录入或 CSV 导入产生，包含日期、方向、金额、分类等要素。

**关键属性**：

| 属性 | 说明 |
|---|---|
| 日期 | 交易发生日期 |
| 方向 | 收入 / 支出 / 转账；转账指账户之间的资金移动（如银行卡转余额宝），**不计入收支统计** |
| 金额 | 保留两位小数 |
| 分类 | 必填，归属一个支出或收入分类（见 5.4） |
| 所属账户 | 选填；填写后可支持按账户维度的统计分析 |
| 数据来源 | 手动录入 / 支付宝账单 CSV 导入 / 微信账单 CSV 导入 / 银行流水文件导入 |
| 备注 | 选填自由文本 |

**与相近概念的区别**：收支记录记录"发生了什么"（流量），资产快照测量"现在有多少"（存量）；收支统计是收支记录在某个预算周期上的聚合结果，资产趋势是资产快照在不同时间点上的对比结果，两组数字允许不一致且通常不一致。"转账不产生收支、只改变资金位置"是本产品全套文档统一的记账规则。

### 5.4 分类

**定义**：对收入与支出进行归类的一组可自定义的层级标签，是收支统计与预算控制的作用维度。

**关键属性**：

| 属性 | 说明 |
|---|---|
| 层级 | 一级分类 / 二级分类；每个二级分类属于唯一一个一级分类 |
| 方向 | 支出分类与收入分类是两套独立体系 |
| 默认与自定义 | 预置学生常用默认分类（支出如餐饮、学习、购物、交通、娱乐；收入如生活费、兼职、红包），支持新增、改名、合并、停用 |
| 映射规则 | 用于 CSV 导入时把账单描述自动匹配到分类的规则（如描述中含关键词"食堂"→餐饮），规则可自定义 |

**与相近概念的区别**：分类是"内容维度"（钱花在什么上），账户是"位置维度"（钱放在哪里），预算周期是"时间维度"（在哪个区间内统计）；同一条收支记录同时携带这三个维度，三者互不替代。

### 5.5 预算周期

**定义**：收支统计与预算管理所用的时间区间，支持"月度"与"自定义"两种形态，双维度并存。

**关键属性**：

| 属性 | 说明 |
|---|---|
| 月度周期 | 自然月（每月 1 日至月末），自动按月滚动生成 |
| 自定义周期 | 用户设定起止日期的任意区间（典型如学期：某年 9 月 1 日至次年 1 月中旬），手动创建与结束 |
| 双维度并存 | 同一时间可同时存在月度视图与一个或多个自定义周期视图，统计与预算进度分别查看 |
| 区间重叠 | 自定义周期可与多个自然月重叠；一条收支记录被计入每一个包含其日期的周期，各周期独立统计 |
| 周期是统计边界 | 记录本身不隶属、不存储于任何周期；修改或删除周期不改动任何收支记录 |

**与相近概念的区别**：预算周期是"统计的时间边界"，不是数据的组织单位；预算是"绑定在某个周期上的金额约束"，同一周期上可分别设置总预算与分类预算。月度与自定义的差异不在数据本身，仅在于自动滚动与手动创建。

### 5.6 储蓄目标

**定义**：用户为某个具体用途设立的攒钱计划，由目标金额、截止日期与已储蓄金额构成。

**关键属性**：

| 属性 | 说明 |
|---|---|
| 目标名称 | 自由文本（如"换笔记本""毕业旅行"） |
| 目标金额 | 用户设定 |
| 截止日期 | 用户设定 |
| 已储蓄金额 | 手动更新，或关联所选账户的资产快照自动取值 [关联取值方案 TBD] |
| 进度 | 已储蓄金额 ÷ 目标金额 |
| 状态 | 进行中 / 已达成 / 已放弃 |

**与相近概念的区别**：储蓄目标是"规划对象"（想达到什么），资产快照是"事实测量"（实际现在有多少），两者允许不一致，其差距正是进度本身；预算是"约束上限"（不要花超），储蓄目标是"达成下限"（要攒到），方向相反、互不推导。

### 5.7 风险等级

**定义**：本产品用于描述用户风险偏好与投资标的风险程度的五级标签体系，可由用户自评得出（偏好侧），或由内容标注（标的侧）。

**关键属性**：

| 属性 | 说明 |
|---|---|
| 等级 | 低 / 中低 / 中 / 中高 / 高，共五级 |
| 与常见评级的对应 | 对应行业常见的 R1～R5（从谨慎型到激进型）评级 [映射细则 TBD]；界面上同时展示浅白描述与等级标签 |
| 用户风险偏好 | 通过自评问卷得出，结果仅为建议值，用户可手动调整 |
| 用途 | 决定配置教育内容中向用户展示的示例比例档位；不构成任何投资建议 |
| 标的侧标注 | 配置教育与 P1 银行产品信息库中，对提及的投资类型按此体系标注典型风险档 |

**与相近概念的区别**：风险等级描述"人（或标的）对波动的承受属性"，储蓄目标描述"事的达成对象"，两者在配置教育中组合使用（不同风险偏好看到不同示例比例），但前者不是后者的输入或输出。

### 5.8 概念速查表

| 概念 | 一句话定位 | 性质 |
|---|---|---|
| 账户 | 资金存放渠道的记账容器 | 持续存在 |
| 资产快照 | 某时刻各账户余额的时点记录 | 时点存量 |
| 收支记录 | 单笔资金进出事件 | 区间流量 |
| 分类 | 收支内容的作用维度 | 归类维度 |
| 预算周期 | 收支统计与预算的时间边界 | 时间区间 |
| 储蓄目标 | 为具体用途设立的攒钱计划 | 规划对象 |
| 风险等级 | 波动承受程度的分级标签 | 属性标签 |

## 6. 产品模块架构总览

### 6.1 模块划分与分期

| 模块 | 分期 | 核心内容 |
|---|---|---|
| 资产汇总 | P0 | 账户管理（三种资产类型：现金与活期、定期与理财产品、基金持仓；不含黄金等贵金属及另类资产）、资产快照、资产总览页（总资产、账户结构、资产趋势图） |
| 收支与预算 | P0 | 收支记录（手动录入 + 支付宝/微信账单 CSV 导入 + 银行流水文件导入）、分类与映射规则、预算周期（月度 + 自定义）、预算进度条与超支提示（页面顶部提示 + 预算卡片内高亮）、收支分类占比图 |
| 储蓄目标与配置教育 | P0 | 储蓄目标管理（进度与状态）、风险偏好自评、配置教育内容（示例比例示意 + 教育性定位声明） |
| 自定义设置 | P0 | 分类自定义、账户自定义、预算规则自定义、风险偏好与目标参数调整 |
| 股票分析 | P1（二期） | 自选股管理、行情展示与基础分析；信息层定位，无实盘交易、无投资建议；行情数据来源与延迟性标记 [TBD] |
| 银行产品信息库 | P1（二期） | 公开信息人工整理的银行产品条目，标注来源与整理日期，未核实数值标记 [TBD] |
| 数据存储与合规（横切） | P0 | 浏览器本地存储、备份文件导出与导入恢复、教育性定位与免责声明体系 |

### 6.2 模块间关系

- **CSV 导入同时服务两个模块**：支付宝/微信账单与银行流水导入后成为收支记录（服务收支与预算模块）；银行流水中若含账户余额信息，可用于核对并辅助更新资产快照（服务资产汇总模块）[余额信息的利用方式 TBD]。
- **自定义设置服务全部 P0 模块**：分类与映射规则作用于收支记录；账户自定义作用于资产汇总；预算规则作用于收支与预算；风险偏好与目标参数作用于储蓄目标与配置教育。
- **储蓄目标与配置教育依赖资产汇总**：储蓄目标的"已储蓄金额"可关联账户的资产快照取值；配置教育引用资产类型与风险等级概念。
- **收支与预算、资产汇总相互独立计算**：收支统计由收支记录聚合而来，资产趋势由资产快照对比而来，两套结果并列展示、互不推导（见 5.2、5.3）。
- **数据存储与合规横切所有模块**：本地存储与备份机制覆盖全部数据；教育性定位声明覆盖全部投资相关内容（配置教育、股票分析、银行产品信息库）。

### 6.3 P0 / P1 边界与分期理由

**边界**：P0 = 资产汇总 + 收支与预算 + 储蓄目标与配置教育 + 自定义设置，构成"记录—统计—规划"的完整闭环；P1 = 股票分析 + 银行产品信息库，为信息消费型扩展。

**分期理由**：

1. **依赖方向**：P1 的两个模块不被任何 P0 模块依赖，缺少它们不影响记账、预算、储蓄目标闭环成立；反过来，银行产品信息库在内容组织上会引用第 5 章的资产类型与风险等级概念，依赖 P0 已建立的术语体系。
2. **数据获取成本**：P0 的数据全部来自用户自有文件与手动输入，可控；P1 依赖外部数据——行情数据的来源与延迟性 [TBD]、银行公开信息的人工整理 [TBD]——获取与维护成本高且存在不可控因素，放二期可为数据方案留出验证时间。
3. **合规成本**：P1 两个模块均为投资相关信息，需要更完整的免责声明与时效标注体系；在 P0 已建立的"教育性信息"定位框架之上再做，成本更低。
4. **验证顺序**：P0 先交付核心的记账与规划价值；P1 的内容广度与深度在 P0 使用情况的基础上决定 [P1 最终范围裁量 TBD]。
